### **Feature 3: AI Viva Interview (System Core)**

This is the core of AIVES: the oral exam itself, run by the AI.

* **Bi-directional Real-time Voice Interaction:** The system converts question text into clear speech using a Text-to-Speech (TTS) service. Students answer directly via a microphone, and their speech is transcribed into text in near real-time via Speech-to-Text (STT).  
* **Adaptive Follow-up Questioning:** Once the transcript is generated, a Large Language Model (LLM) analyzes the answer content to detect ambiguity, missing points, or logical contradictions. When it finds one, it writes a follow-up question about that point, the way a lecturer asks for more.  
* **Automated Session Management:** Only students on the session's participant list can start an attempt, only inside the session's time window, and only once. The system keeps each student's attempt separate, runs a countdown in seconds for every answer (follow-up answers included), and stops asking follow-up questions once a main question reaches its limit. When the time window ends, the session closes on its own: attempts in progress stop at once, and unanswered questions count as 0 (a question the student never reached has no stored response and simply adds 0 to the total).  
* **Rubric-based Scoring Support:** Once a main question and its follow-ups are completed, the LLM suggests a per-question score and comments based on the question's rubric. The suggested score remains pending until a lecturer reviews it.  
* **Lecturer Review & Final Score Approval:** Lecturers read the transcript with the AI-suggested score and comments for each question, then confirm one final score for the whole attempt. That score starts as the total of the AI's per-question scores; the lecturer may change it and add a comment before confirming. The AI only supports grading; the lecturer always makes the final decision.  
* **Exam Record:** Every turn (the question asked, the transcribed answer and the timestamps) is stored in the database, and the answer audio is kept in Object Storage, so a grade can be checked later against what was said.

### **Feature 6: Feedback & Reporting**

This feature turns stored exam results into reports for students and statistics for lecturers. It reads stored scores only and never calls the AI again.

* **Student Exam Report:** After the lecturer confirms the final score, students can review their report: the AI-suggested score and comments for each question, the lecturer's final score for the whole attempt, and the complete dialogue history (primary questions, follow-up inquiries, and transcribed responses). Until the lecturer confirms, the report shows that it is waiting for review.  
* **Class Statistics:** Lecturers see the hardest questions and the good-answer rate (from the AI's per-question scores) and the score distribution (from the lecturers' final scores). Only attempts with a confirmed final score are counted.  
* **Grade Sheet Export:** Lecturers export the class grade sheet in the school's template. It uses confirmed final scores only; attempts still waiting for review are marked as pending.

### **Feature 7: Access Control & Exam Configuration**

In the course feature list this group is called "System Administration". It covers accounts, sign-in, courses, exam setup and the AI settings.

* **User Management & Role-Based Access Control (RBAC):** Administrators create user accounts, change a user's role (Student, Lecturer, Administrator) and deactivate accounts; they also create and edit courses and assign lecturers to them. Each lecturer can only open the courses they are assigned to.  
* **Registration and Accounts:** Anyone can register with an account name, an email and a password. A registered account gets the Student role, is not linked to Google, and must confirm its email through a verification link before it is ready. The account name never changes; the username (the display name) starts as the account name, can be changed in Account Settings, and does not have to be unique. Account Settings also let users create an account name and password if they have none yet, and link their Google account (the Google email must match the account email).  
* **Authentication:** Users sign in either with their Google account (SSO) or with their account name or email plus password. Only active accounts can sign in. On the first Google sign-in, the system creates the account (Student, linked to Google, username taken from the part of the email before @) and asks whether to create an account name and password now: if yes, it emails a link that opens a form for both; if the user chooses later, they sign in with Google only until they create them in Account Settings. A Google sign-in on an existing account that is not linked to Google shows a message instead. When an administrator creates an account, the system emails the user a link to set the account name and password. The two kinds of email link do different things: an account-setup link sets the account name and the password, while a password-reset link only sets a new password and never changes the account name. Users who forget their password ask for a link from the login page, and the system shows the same message whether or not the email is registered. An account that already has a password gets a reset link; an account without a password yet (for example, one whose setup link expired) gets an account-setup link instead. Opening either link also confirms the email, so an account whose verification link expired can recover this way. Every email link (email verification, account setup, password reset) can be used only once and expires. Passwords are never stored in plain text: each password is hashed together with a unique random salt, and only the salt and the hash are stored. At login, the entered password is hashed with the stored salt and compared with the stored hash.  
* **STT/TTS Language Configuration:** Allows administrators to configure the language (Vietnamese/English) used by the STT and TTS services.  
* **Exam Session Setup:** Lecturers create exam sessions with a time window, load the main question list, define a grading rubric for each question (one score per question), set the time limit per answer in seconds and the maximum number of follow-ups, import the list of students who may take the session, and publish it. Rows of the student list that match no account are skipped and reported. A session can be published only when it has at least one question, every question has a rubric and at least one student is on the list; once published, its questions and rubrics are locked. A draft can be opened again later to finish the setup.  
* **AI Provider Settings & Audit Log:** Administrators choose the STT, TTS, and LLM providers and set their API keys and endpoints. The system keeps an audit log of important administrative actions, which administrators can open from their workflow.
